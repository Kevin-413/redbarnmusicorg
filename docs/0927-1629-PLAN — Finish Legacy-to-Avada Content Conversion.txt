# PLAN — Finish Legacy-to-Avada Content Conversion

## Goal

Finish converting the Red Barn Music School website so normal public pages use native Avada Builder content and reusable Avada Library sections, with no unnecessary dependency on Gutenberg reusable blocks, raw HTML wrappers, or legacy page-builder structures.

A large amount of the site has already been converted. This plan is **not** a rebuild. First inventory what is already complete, then convert only what remains.

## 1. Inventory the Current Site

Review the current `redbarnmusicorg-avada` site and classify every public page as:

- Fully native Avada
- Avada page using Avada Library sections
- Mixed Avada + Gutenberg
- Gutenberg/plain WordPress content
- Legacy Fusion/shortcode content
- Dynamic content generated by an RBM plugin
- Intentional third-party content such as Forminator

Do not change anything during this inventory.

Create a concise table containing:

- Page title
- Page ID
- Current editor/content type
- Template
- Avada Library sections already used
- Remaining legacy/Gutenberg content
- Recommended action
- Status: Complete / Needs Cleanup / Needs Conversion

## 2. Inventory the Avada Library

List the existing Avada Library sections and determine which public page content has already been extracted.

Include at least:

- Library item name
- Library item ID
- Type
- Page(s) using it
- Whether it is currently active
- Whether it contains native Avada Builder elements
- Whether it contains embedded Gutenberg, raw HTML, legacy markup, or temporary CSS fixes
- Whether it should remain reusable

Do not recreate Library sections that already exist and work correctly.

## 3. Define the Target Architecture

The target for ordinary public pages is:

```text
Avada page/template
    +
native Avada Builder containers/elements
    +
Avada Library sections where reuse is useful
    +
RBM shortcodes only for genuinely dynamic content
    +
third-party shortcodes only where required
```

Avoid unnecessary use of:

```text
Gutenberg reusable blocks
wp:html wrappers
raw Fusion content embedded inside Gutenberg
legacy page-builder structures
duplicated page content
page-specific CSS patches that Avada settings can replace
```

Do not remove working dynamic RBM functionality simply to make a page "pure Avada."

## 4. Home Page

The six existing homepage sections have already been moved into Avada Library items:

- Lessons Starting Now
- Open House
- Amherst Block Party
- Gallery
- Scholarships
- What Families Say

Do not recreate those sections.

Review the remaining Home page structure and identify anything still dependent on Gutenberg reusable block `20440`, including the Welcome content and separators.

Create or reuse native Avada Library content for anything worth preserving as a reusable section.

Final goal:

```text
Home
├── Home - Welcome
├── Lessons Starting Now
├── Open House
├── Amherst Block Party
├── Gallery
├── Scholarships
└── What Families Say
```

The public Home page should ultimately be assembled directly in Avada rather than depending on Gutenberg reusable block `20440`.

Preserve block `20440` as a rollback backup until the new Home page has been verified.

## 5. Review Already-Converted Pages First

Before converting anything else, identify pages that are already effectively complete.

If a page is already native Avada and visually correct:

**leave it alone.**

Do not rebuild working pages merely to standardize minor implementation differences.

Only clean up a completed page if it still has a meaningful dependency on:

- Gutenberg layout blocks
- raw HTML wrappers
- obsolete legacy code
- duplicated content
- temporary migration CSS

## 6. Convert Remaining Pages

After the inventory, convert only pages classified as needing work.

Known pages requiring review include:

- Reviews
- Contact Us
- Community Links
- Policies

There may be others discovered during inventory.

For each page:

1. Preserve the current page/content.
2. Identify its visible content and dynamic functionality.
3. Reuse existing Avada Library sections wherever possible.
4. Create new Library sections only when the content is genuinely reusable.
5. Rebuild remaining layout using native Avada elements.
6. Keep required RBM/Forminator shortcodes intact.
7. Compare the rendered result with the existing page.
8. Switch the public page only after verification.

## 7. Contact Us

There are currently two Contact Us page implementations.

Before making any changes:

- identify both page IDs
- identify which one is currently public/canonical
- identify which contains the current Forminator form
- compare their content and functionality

Recommend which should become canonical, but do not delete either page during this phase.

The final Contact page should use native Avada layout around the required Forminator content.

## 8. Reviews

Review the current Reviews page and determine what portion is still Gutenberg or `wp:html`.

Preserve the current reviews and appearance.

Convert the page structure to native Avada elements where practical.

Reviews themselves may remain normal text/content inside Avada Text elements unless there is a better existing reusable structure.

Do not change review wording during this project.

## 9. Policies and Community Links

These pages appear to contain relatively simple/plain content.

Convert their presentation to native Avada containers and elements while preserving:

- wording
- links
- headings
- page width
- current visible layout

Policies should continue to fit within the established interior-page header/content frame.

## 10. Standard Page Templates

Do not place normal page-specific content inside PHP templates.

Templates should control site structure such as:

- header
- page-title area
- content frame
- sidebar/no-sidebar arrangement
- width
- spacing
- footer

Page content should live in Avada Builder pages or Avada Library sections.

Retain the existing standard page templates unless inspection finds a specific problem.

## 11. Temporary CSS and Migration Fixes

Identify CSS that was introduced specifically to make converted legacy layouts behave like the original.

Example: the custom responsive/layout CSS currently associated with the Lessons Starting Now section.

Do not remove working fixes immediately.

For each one:

- document why it exists
- determine whether native Avada settings can replace it
- replace it only if the rendered result remains equivalent
- otherwise leave it in place and mark it for later cleanup

This conversion project should prioritize correctness over cosmetic code cleanup.

## 12. Links and Media

While reviewing converted content, identify:

- `.local` URLs remaining in saved content
- obsolete `/lessons/` links
- outdated image URLs
- incorrect internal links
- image references that should use Media Library attachment IDs
- external links that should intentionally open in a new tab

Do not perform broad search-and-replace without confirming the intended destination.

Report these separately from the Avada conversion work.

## 13. Preserve Dynamic Content

Do not flatten or manually copy dynamic content generated by RBM plugins.

Examples include:

- Faculty
- Instruments
- forms
- other current RBM shortcodes

Avada should provide the page/layout shell while the plugin remains responsible for dynamic data.

## 14. Verification

For every page changed:

- compare before and after visually
- verify desktop layout
- verify mobile layout
- verify buttons
- verify images
- verify internal links
- verify external links
- verify anchors
- verify forms
- verify RBM shortcodes
- verify no raw shortcode is displayed publicly
- verify no page content disappeared

Where practical, compare rendered output rather than only comparing database content.

## 15. Rollback

Before modifying a page or reusable section:

- preserve its current content
- record page/Library ID
- do not delete legacy versions during conversion

Only remove obsolete structures after the converted site has been fully verified.

## 16. Deliverables

Before making changes, return an inventory and proposed conversion list.

The report should clearly separate:

### Already Complete
Pages that should not be touched.

### Minor Cleanup
Pages already using Avada but containing a small amount of legacy/Gutenberg material.

### Conversion Required
Pages that still materially depend on Gutenberg or legacy structures.

### Dynamic / Intentional
Pages containing RBM or third-party shortcodes that should remain.

### Avada Library
Existing sections, their IDs, usage, and any sections still needed.

### Recommended Conversion Order
A safe order for completing the remaining work.

## 17. Important Scope Rule

**Do not rebuild content that is already successfully converted to Avada.**

This project is primarily:

```text
inventory
→ identify remaining legacy dependencies
→ extract only what is still needed
→ assemble pages cleanly in Avada
→ verify
```

The desired result is a maintainable Avada website, not a second migration of work that has already been completed.

## Suggestions

Reviewed for clarity and function. The overall structure (inventory first,
convert only what's needed, verify, don't rebuild working pages) is sound.
A few points worth clarifying or adding before execution:

1. **Section 4 (Home Page) is slightly stale.** It lists "Gallery" as one
   of the six existing sections; the actual Library item is titled
   "Gallery Spring Recital pics" (ID 20868). Minor, but worth using exact
   titles/IDs so the inventory table in Section 1 isn't ambiguous.

2. **"Home - Welcome" is undefined.** Section 4's target diagram introduces
   a new Library section called "Home - Welcome" but doesn't say what it
   should contain (likely just the intro quote currently in block 20440).
   Recommend defining its exact content before creating it, so it isn't
   invented ad hoc during conversion.

3. **Duplicate Library titles need ID-based disambiguation.** At least two
   pairs of Library items already share a title: "Gallery" (IDs 20890 and
   20915) and, if reused elsewhere, "Contact Us" (20883/20884 differ by
   sub-purpose but overlap in naming). Section 2's inventory table should
   require the Library item ID as the primary key, not the title, to avoid
   the confusion already seen once during the demo-page work.

4. **"Canonical" page determination method is unspecified.** Section 7
   says to identify which Contact Us page is "currently public/canonical"
   but doesn't say how (nav menu reference, canonical URL/redirect, Yoast
   sitemap inclusion, etc.). Recommend explicitly stating the check order,
   e.g.: (a) is it linked from the primary nav menu, (b) does it have a
   canonical/noindex setting pointing elsewhere, (c) which slug matches
   external links/backlinks.

5. **No explicit per-page approval gate.** Section 16 says to return an
   inventory before changes, but with ~6+ pages in scope, recommend stating
   that each page conversion is its own change-set/approval step (per the
   project's one-change-set-per-message rule), rather than approving the
   whole list once and converting pages back-to-back.

6. **SEO metadata preservation isn't called out.** Earlier page work (e.g.
   the Gallery conversion) explicitly required preserving SEO metadata,
   slug, and page ID. This plan's Section 14 verification list should add
   "SEO title/meta description/canonical/noindex unchanged" alongside the
   existing visual/functional checks.

7. **Production/live site sync is out of scope but not stated.** The plan
   only mentions `redbarnmusicorg-avada` (Local). Worth adding one line
   confirming this plan does not include pushing changes to
   `redbarnmusic-live`, so that stays a clearly separate, later decision.

8. **Minor addition to verification (Section 14):** consider adding a check
   for duplicate HTML `id` attributes when the same Library section (e.g.
   an imageframe or button) is referenced on more than one page, since
   Avada Library items can carry static IDs that collide if reused broadly.

No other structural or scope concerns; the plan otherwise matches how the
Home page conversion was already carried out (see
`docs/0927-1622-Copilot-REPLY-Extract-Home-Page-Sections-To-Avada-Library.txt`).
